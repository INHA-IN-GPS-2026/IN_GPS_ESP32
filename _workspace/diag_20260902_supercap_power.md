## 2. 원인 후보 (확률 순)

### 1순위 — 측정 조건 불일치 (V_start / 컷오프 판정). 코드 문제가 아닐 가능성이 가장 높다

**근거 A — "지속시간"은 펌웨어가 정의하지 않는다.**
컷오프 판정 로직이 펌웨어에 **없다**. 전압 감시 코드가 전무하고(`PIN_BAT_LBO`/`PIN_BAT_ALERT`는 `board_pins.h:74-77`에서 "이 버전 미구현"), 컷오프는 전적으로 하드웨어 슈퍼바이저다:
- BOD는 `sdkconfig:1448` `CONFIG_ESP_BROWNOUT_DET_LVL_SEL_7=y` (≈2.44V) — 그러나 이건 **부스트 출력인 3.3V 레일** 기준이다.
- 실제로 먼저 끊는 건 SW_REG의 TPS3839G25. `V_off≈2.52V / V_on≈3.07V`, 히스테리시스 ≈555mV (근거: 회로도 벡터 추적 메모 `project_ingps_rev40_board_facts` #1 — **도면 근거, 실측 미검증**. `Docs/INGPS_슈퍼캡_축전시간_분석_2026-08-11.md` §6-2는 이를 "히스테리시스 없음"이라 반대로 적고 있어 문서 쪽이 낡았다).

즉 **양쪽 빌드의 컷오프 전압은 하드웨어가 같게 잡는다.** 차이는 오직 시작 전압과 "언제 끝났다고 볼 것인가"의 판정에서 나온다.

**근거 B — 슈퍼캡 에너지는 전압의 제곱이라, V_start 차이가 지속시간을 통째로 뒤집는다.**
`E = ½C(V₁²−V₂²) = 0.235 × (V₁²−V₂²)` [J]

| V_start | V_end | 가용 E | 130초에 걸리면 평균전류 환산 |
|---:|---:|---:|---:|
| **4.61 V** (#2 기록값) | 3.30 V | 2.435 J | **4.74 mA** |
| 4.00 V | 3.30 V | 1.201 J | 2.53 mA |
| 3.60 V (배터리 만충) | 3.30 V | 0.486 J | 1.08 mA |
| 3.37 V (R5로 130s 충전, τ=47s) | 3.30 V | 0.110 J | **0.25 mA** |

**같은 "130초"가 V_start 하나로 0.25 mA ~ 4.74 mA 사이 어디든 될 수 있다.**
#2는 4.61V에서 출발한 완전충전 방전이다. #1이 같은 4.61V에서 출발했는지가 확인되지 않는 한, 130 vs 210 비교는 성립하지 않는다. 특히 #1을 배터리/R5로 충전했다면 τ = R5·C6 = 47s(같은 문서 §2)라 아무리 기다려도 3.6V를 못 넘는다 → 시작 에너지가 5배 이상 작다 → **소비전류가 #2보다 낮아도 130초에 죽는다.**

**근거 C — `I = C·ΔV/t` 자체가 이 회로에서 편향된 추정치다.**
부하가 부스트 컨버터(TPS61131, `Docs/…축전시간_분석…md` §3-2 그림)라 **정전류가 아니라 정전력**이다. 캡 전압이 내려가면 입력전류가 올라간다. 따라서 "평균전류"는 관측 창(V₁→V₂)에 의존하는 값이고, 창이 다른 두 측정의 평균전류를 직접 비교할 수 없다.

**반증 방법:** #1 실행의 V_start / V_end / 시간 3개를 확보해 §3-1 표를 채운다. 없으면 §3-2 절차로 재측정.
**확인 시 고칠 파일:** 없음(측정 프로토콜 문제). `Docs/INGPS_floor전류_측정절차_2026-08-11.md`에 창 고정 절차를 명시할 것.

### 2순위 — 워치독: **재부팅이 아니라 "wake 주기"가 진짜 비용이다**

사용자 가설("BLE 스택 미기동하면 재부팅 트리거")을 코드로 검증했다. **결론: L1 자가복구 재부팅 경로는 이미 막혀 있다.** 다만 워치독이 전력에 기여하는 **다른** 경로가 실재한다.

#### 2-a. 재부팅 가설 — 코드상 성립하지 않는다 (막혀 있음)

BLE-off 빌드의 두 heartbeat가 어떻게 되는지 추적:

| 슬롯 | kick 주체 | BLE-off 시 | 판정 |
|---|---|---|---|
| `WDT_HB_ADV` | `adv_cycle_task` (`ble_adv.c:290, 322`) | 없음 | `app_main.c:339`가 stale을 **24h**로 올림 → `wdt_guard.c:335`가 arm → 24시간 무사 |
| `WDT_HB_ACCEL` | `build_mfg_data()` (`ble_adv.c:104`) | 없음 | `last_us`가 **0으로 남음** → `wdt_guard.c:211-214`가 `last==0` 슬롯을 **검사에서 건너뜀** → 영원히 안 걸림 |

순서도 맞다 — `app_main.c:339-340`(stale 완화)이 `:349`(`wdt_guard_boot_done()`, ADV 시계 arm)보다 **먼저** 실행된다. `wdt_guard_set_hb_stale()`(`wdt_guard.c:172-177`)은 "느슨해지는 방향만 허용"이라 24h(86,400,000ms)를 그대로 받는다. 비교식 `now - last > (int64_t)stale_ms * 1000`(`:217`)도 int64로 승격되어 오버플로 없음.

**→ #1 빌드가 130초 안에 L1 자가복구 재부팅을 할 코드 경로는 없다.**
L2 Task WDT(8s, `wdt_guard.c:297`)도 `wdt_monitor_task`가 2초마다 `esp_task_wdt_reset()`(`:201`)을 치고, app_main 태스크는 `:340`에서 해제되므로 굶지 않는다.

> ⚠ 단, 이건 **코드 논리**다. 실제로 재부팅 중인지는 부팅 로그의 reset reason으로만 확정된다 → §3-3.

#### 2-b. 진짜 워치독 비용 — BLE-off 빌드에서 `wdt_monitor_task`가 **유일한 주기적 waker**다

먼저 사용자 질문 ①에 대한 사실: **light sleep 경로에 `esp_sleep_enable_timer_wakeup()`은 없다.**
전체 grep 결과 호출은 3곳뿐이고 전부 **deep sleep 전용**이다:
- `app_main.c:186-187` — `INGPS_CAP_CHARGE_TEST` (현재 0, 미사용)
- `wdt_guard.c` crash-loop 백오프 2곳 (`esp_deep_sleep_start()` 직전)

light sleep은 `esp_pm_configure(.light_sleep_enable=true)`(`app_main.c:278-283`) + tickless idle(`sdkconfig:1849`)에 의한 **자동 진입**이다. 따라서 **wake 주기 = 시스템에서 가장 짧은 태스크 지연**이다.

BLE-off 빌드에 남아 있는 주기적 태스크를 전수 조사한 결과:

| 태스크 | 주기 | 존재 조건 |
|---|---|---|
| `adv_cycle_task` | 1s (`ADVM_DEF_MV_MS`) | `on_sync()`에서 생성 → **BLE-off면 생성 안 됨** (`app_main.c:59-88`이 `#if !INGPS_BLE_DISABLED`) |
| `pm_debug_task` | 15s | `INGPS_PM_DEBUG 0` → 없음 |
| `cap_test_task` | — | `INGPS_CAP_CHARGE_TEST 0` → 없음 |
| **`wdt_monitor_task`** | **2000ms** (`wdt_guard.c:89, 200`) | **항상** |

**→ BLE-off 빌드에서 칩을 깨우는 것은 워치독 헬스모니터 하나뿐이다.** (부수 확인: `build_mfg_data()`가 `adv_cycle_task`에서만 호출되므로, 이 빌드는 사실 **센싱을 전혀 하지 않는다** — 부팅 시 `as6221_init()`/`adxl345_init()`만 하고 이후 I2C 트랜잭션이 0건이다. "센싱만" 이라는 실험 라벨과 실제 동작이 다르다.)

매 wake마다 확정적으로 지불되는 비용(전부 sdkconfig 근거):

| 항목 | 설정 | 근거 |
|---|---|---|
| 플래시 ready 추가 대기 **2 ms** | `CONFIG_ESP_SLEEP_WAIT_FLASH_READY_EXTRA_DELAY=2000` | `sdkconfig:1399` |
| RTC 발진기 **매 사이클** 재캘리브 | `CONFIG_PM_LIGHTSLEEP_RTC_OSC_CAL_INTERVAL=1` | `sdkconfig:1532` |
| CPU 전원차단 후 복원 + 캐시 tagmem 복원 | `CONFIG_PM_POWER_DOWN_CPU_IN_LIGHT_SLEEP=y`, `CONFIG_PM_RESTORE_CACHE_TAGMEM_AFTER_LIGHT_SLEEP=y`, `CONFIG_PM_POWER_DOWN_TAGMEM_IN_LIGHT_SLEEP=y` | `sdkconfig:1533, 1534, 2735` |

0.5 Hz × (수 ms 액티브)면 duty 0.1~0.3% 수준이라 **단독으로 mA를 만들지는 못한다.** 그러나 이 빌드의 floor를 재는 실험에서는 **유일한 오염원**이므로, 끄고 재는 것이 실험 설계상 옳다. → §5에서 스위치를 만들었다.

**⚠ 방향 주의:** 이 항목은 #1이 #2보다 **나쁠** 이유가 아니다. #2(BLE 기동)는 1초마다 adv 사이클 + ADXL345 FIFO 32샘플 드레인(100kHz I2C로 ~20ms) + AS6221 2회 읽기 + TX를 하므로 wake 빈도도 액티브 시간도 #1보다 **훨씬 크다.** 순수 펌웨어 논리로는 #1이 반드시 더 낮아야 한다. 이것이 §1순위(측정 조건)를 1순위로 올린 이유다.

#### 2-c. 진짜 갭 — 브라운아웃 재부팅 루프는 **crash-loop escalation에 잡히지 않는다**

`wdt_guard.c:230-233`:

```c
if (s_rtc.magic != WDT_RTC_MAGIC ||
    rr == ESP_RST_POWERON || rr == ESP_RST_BROWNOUT) {
    s_rtc.abnormal_resets = 0;      /* ← BROWNOUT이 카운터를 0으로 되돌린다 */
```

슈퍼바이저가 EN을 내렸다 올리는 히컵 루프는 `ESP_RST_POWERON` 또는 `ESP_RST_BROWNOUT`으로 들어온다 → **매번 카운터가 0으로 리셋** → 백오프 딥슬립도 SAFE 모드도 영원히 발동하지 않는다. 부팅 1회당 `E_boot` ≈ 0.45 J(같은 문서 §9-2 추정)를 계속 태운다. 슈퍼캡 가용 에너지가 2.4 J이면 **5~6회 부팅으로 소진**된다.

`Docs/…축전시간_분석…md` §6-2가 정확히 이 고장 모드를 "3.3V 레일이 정상적으로 꺼지므로 BOD 로그도 안 남고 진단이 어렵다"고 경고한 그것이다. 이 시나리오는 **#1이 130초에 죽은 것을 단독으로 설명할 수 있다.**
**반증 방법:** §3-3 (부팅 로그의 reset reason 카운트).
**확인 시 고칠 파일:** `main/watchdog/wdt_guard.c:230-233` — BROWNOUT을 POWERON과 분리해 별도 카운터로 세거나, 최소한 로그로 남길 것. (지금은 고치지 않음 — 진단 확정 전.)

### 3순위 — 슬립 중 상시 전류: PSRAM 16MB 미초기화 + 플래시 파워다운 미적용 + ADXL345 상시 measure

사용자 질문 ③(PSRAM/sdkconfig 불일치)에 대한 **정정된 사실**부터:

```
sdkconfig:1541   # CONFIG_SPIRAM is not set
sdkconfig:2736   # CONFIG_ESP32S3_SPIRAM_SUPPORT is not set
```

`CONFIG_SPIRAM_MODE_*` 도 `CONFIG_SPIRAM_SIZE` 도 **sdkconfig에 심볼 자체가 존재하지 않는다**(SPIRAM이 꺼져 있으면 하위 심볼이 생성되지 않음). 검색에 걸린 `CONFIG_SOC_SPIRAM_SUPPORTED` / `CONFIG_SOC_PSRAM_DMA_CAPABLE`(`sdkconfig:240, 37`)은 **칩 capability 상수**이지 설정이 아니다.

> 메모리(`project_ingps_esp32_hw_flash`)의 "sdkconfig는 2MB"는 **플래시 크기** 이야기이며, 이미 `sdkconfig:572` `CONFIG_ESPTOOLPY_FLASHSIZE="16MB"`로 수정되어 있다. **PSRAM 크기 설정 불일치는 현재 존재하지 않는다.**

**→ 사용자 질문 ③의 시나리오("설정이 실제 칩과 달라 light sleep 시 PSRAM이 절전에 못 들어간다")는 기각.** IDF가 PSRAM을 인식조차 하지 않으므로 "잘못된 크기로 절전 진입" 자체가 일어나지 않는다.

**그러나 사용자 확인(16MB PSRAM 실장)과 결합하면 더 나쁜 결론이 나온다:**
옥탈 PSRAM 다이는 모듈 내부에서 VDD_SPI(플래시와 공용, 상시 급전)에 물려 있는데, 펌웨어가 SPIRAM을 켜지 않으므로 **초기화도, deep power-down 명령 발행도 하지 않는다.** PSRAM은 POR 직후 standby/self-refresh 상태로 남아 **액티브·light sleep·deep sleep 전 구간에서 전류를 계속 먹는다.** 소프트웨어로 끌 방법이 없다(SPIRAM을 켜야 명령을 보낼 수 있으므로).

이것은 **양쪽 빌드에 동일**하므로 역전을 설명하지 못한다. 하지만 floor가 설계 가정 240µA(`Docs/INGPS_1yr_firmware_design.md:27, 48`)가 아니라 **mA급**으로 나오는 이유의 유력 후보다.

같은 성격의 상시 항목 3건 추가:

| 항목 | 근거 | 비고 |
|---|---|---|
| light sleep에서 **플래시 파워다운 안 함** | `sdkconfig:1394` `# CONFIG_ESP_SLEEP_POWER_DOWN_FLASH is not set` | 설계문서 §8(`INGPS_1yr_firmware_design.md:95`)은 "flash power-down in light sleep"을 **요구사항으로 명시** → **설정이 설계와 어긋나 있다** |
| 플래시 누설 워크어라운드 + MSPI 전 IO 풀업 유지 | `sdkconfig:1395, 1396` | 슬립 중 MSPI 라인이 풀업 유지 |
| ADXL345가 **영원히 measure 모드** | `adxl345.c:150` `reg_write8(REG_POWER_CTL, PWR_MEASURE)` | 전원 게이팅 회로 없음, INT1/INT2 도면상 미접속(`board_pins.h:66-73` + 보드 메모 #2). BLE-off 빌드는 FIFO를 **한 번도 드레인하지 않으면서** 이 전류를 계속 낸다 |
| AS6221 ×2 연속변환 | `as6221.c:34` (SM=0), 주석상 4conv/s typ 6µA | 상대적으로 작음 |

### 4순위 — 32.768 kHz 크리스털 미기동 (조용한 내부 RC 폴백)

```
sdkconfig:1410  CONFIG_RTC_CLK_SRC_EXT_CRYS=y
sdkconfig:944   CONFIG_BT_CTRL_LPCLK_SEL_EXT_32K_XTAL=y
```

`board_pins.h:42-49`가 명시적으로 경고한다 — 크리스털이 안 뜨면 IDF가 **조용히 내부 RC로 폴백**하고 "그 순간 평균전류가 µA대에서 mA대로 튄다."
`sdkconfig.defaults:24-30`의 표: MAIN_XTAL ~21 mA / RTC_SLOW ~4 mA / EXT_32K "최선".

**실측 2.93 mA는 목표 457 µA의 6.4배이고, 표의 RTC_SLOW(~4 mA) 행에 훨씬 가깝다.** 크리스털이 실제로는 안 뜨고 있을 가능성을 배제할 수 없다.
양쪽 빌드에 동일하므로 역전은 설명 못 하지만, **절대 크기(왜 mA급인가)의 유력 후보**다.
비대칭 요소 하나: BLE-off 빌드는 BT 컨트롤러를 초기화하지 않으므로 `BT_CTRL_LPCLK_SEL_EXT_32K_XTAL`이 아예 적용되지 않는다. 시스템 RTC slow clock(EXT_CRYS)은 양쪽 동일하다. 이 차이가 전력에 유의미한지는 **미확인**.
**반증 방법:** `sdkconfig.defaults:39-42`가 제시한 절차 — R5(100Ω) 양단 전압으로 평균전류 역산(457µA면 46mV).
**확인 시 고칠 파일:** 하드웨어(X1/C11/C12 실장·납땜). 폴백이 확정되면 펌웨어로는 못 고친다.

### 5순위 — 브라운아웃/최소 동작 전압 차이 (사용자 질문 ④): **코드상 두 경로가 다를 이유가 없다**

- 센서와 BLE는 **둘 다 부스트 출력인 3.3V 레일**을 쓴다. 별도 아날로그 레퍼런스 경로가 없다(rev 4.0에서 ADC 네트가 전부 사라짐 — `main/CMakeLists.txt`의 `adc_cal.c` 주석, `board_pins.h:38-39` 미접속 목록).
- AS6221 최소 1.71V, ADXL345 최소 2.0V로 둘 다 3.3V 레일 컷오프보다 한참 아래 → "센서가 BLE보다 높은 전압을 요구해서 먼저 죽는다"는 시나리오는 성립하지 않는다.
- 오히려 **부하가 가벼울수록 부스트가 더 낮은 입력전압까지 3.3V를 유지**하므로, 저전류 빌드가 **더 오래** 버텨야 한다 — 관측과 반대 방향이다.
- BOD LVL7(`sdkconfig:1448, 1455`, ≈2.44V)은 부스트 출력 레일 기준이라 SW_REG 슈퍼바이저(≈2.52V)가 먼저 EN을 내린다 → BOD는 사실상 발화하지 않는다(`sdkconfig.defaults:52-53` 주석과 일치).

**→ 이 후보는 기각.** 단, 슈퍼바이저 임계·히스테리시스는 **도면 근거이고 실측 미검증**이다(§3-4).

## 3. 사용자 확인 요청 (읽기 전용 — 코드 수정 불필요)

### 3-1. 🔴 최우선 — #1(130초) 실행의 전압 창 복원

| 항목 | 값 | 비고 |
|---|---|---|
| #1 V_start | ? | #2는 **4.61 V** |
| #1 V_end (판정 기준) | ? | #2는 **3.30 V** |
| #1 지속시간 | 130 s | |
| #1 충전원 | 외부 전원? 배터리+R5? | 배터리라면 3.6V를 못 넘는다(τ=47s) |

`discharge08260.csv`에 대응하는 #1 쪽 CSV가 있으면 그것으로 충분하다. 저장소에는 두 파일 다 없다.
**판정 기준:** V_start·V_end가 #2와 동일(4.61→3.30)해야만 "130 vs 210"이 유효 비교다. 다르면 **역전 현상 자체가 소멸**하며, 아래 표로 실제 평균전류를 다시 계산해야 한다.

`I_avg ≈ C·(V_start − V_end)/t = 0.47 × ΔV / t` [A]
`E = 0.235 × (V_start² − V_end²)` [J]

### 3-2. 재측정 프로토콜 (두 빌드를 같은 창에서)

1. 두 빌드 모두 **같은 외부 전원**으로 캡을 같은 전압(예: 4.50 V)까지 충전하고 전원 분리.
2. 배터리는 **분리**(R5 트리클이 섞이면 캡 단독 방전이 아니다).
3. 종료 판정은 **동일 전압**(예: SW_REG 3.30 V 도달)으로 고정. "안 보인다/응답 없다"로 판정하지 말 것.
4. 스코프/데이터로거로 V(t) 곡선 전체 저장 → 순간전력 `P(t) = −C·V·dV/dt` 로 비교. 평균전류 한 숫자로 비교하지 말 것(부스트는 정전력 부하다, §2-1순위 근거 C).

### 3-3. 🔴 재부팅 루프 여부 — UART 로그 1줄로 갈린다

`app_main.c:236`이 `esp_log_level_set("WDT_GUARD", ESP_LOG_INFO)`로 이 태그만 열어두므로, 전역 묵음 빌드에서도 부팅마다 다음이 찍힌다:

```
WDT_GUARD: reset reason=<N>, consecutive abnormal resets=<M>
```

- 130초 동안 이 줄이 **1회만** → 방전이 맞다. 재부팅 아님.
- **여러 번 반복** → 재부팅 루프. 이때 `reset reason` 숫자가 결론을 가른다:
  | reason | `esp_reset_reason_t` | 해석 |
  |---|---|---|
  | 1 | `ESP_RST_POWERON` | 슈퍼바이저 히컵 (EN 껐다 켬) → §2-2c |
  | 3 | `ESP_RST_SW` | `wdt_guard_reboot()` — L1 자가복구. **코드상 나올 리 없다**(§2-2a). 나오면 내 분석이 틀린 것이니 알려줄 것 |
  | 4 | `ESP_RST_PANIC` | 패닉 → 백트레이스 동봉 |
  | 5 | `ESP_RST_INT_WDT` | INT WDT 300ms |
  | 6 | `ESP_RST_TASK_WDT` | Task WDT 8s |
  | 7 | `ESP_RST_WDT` | 기타 WDT |
  | 9 | `ESP_RST_BROWNOUT` | BOD 발화 |

  ⚠ 단 `consecutive abnormal resets`는 POWERON/BROWNOUT에서 0으로 리셋되므로(§2-2c) **이 숫자를 신뢰하지 말고 줄이 몇 번 찍히는지를 세라.**

> UART를 붙이면 전류가 올라가 지속시간이 짧아진다. **이 실험은 "재부팅 여부 판정" 전용**이고, 지속시간 숫자는 여기서 얻지 말 것.

### 3-4. sdkconfig / 하드웨어 확인 항목

| # | 확인 대상 | 방법 | 정상 판정 |
|---|---|---|---|
| 1 | 32.768 kHz 크리스털 실동작 | R5(100Ω) 양단 DC 전압을 DMM으로 (`sdkconfig.defaults:39-42`) | 457 µA면 **46 mV**. 수백 mV~V면 폴백 발생 |
| 2 | PSRAM standby 전류 | 슬립 중 3.3V 레일 전류에서, 모듈 VDD_SPI 계통 기여분 분리 (가능하면 PSRAM 미실장 모듈과 대조) | 데이터시트 standby 대비 판정 |
| 3 | 슈퍼바이저 V_on / V_off | 캡 완전방전 → 서서히 충전하며 EN 핀과 SW_REG 동시 관측 | V_on≈3.07 / V_off≈2.52, 히스테리시스≈555mV (도면 추정치) |

## 4. 결론이 안 나는 부분 (관측 불가 — 단정하지 않음)

- **#1의 실제 소비전류를 나는 알 수 없다.** V_start/V_end 기록이 없어 130초를 전류로 환산할 방법이 없다. "역전이 실재하는가" 자체가 **미확정**이다.
- **재부팅 여부는 정적 분석으로 확정 불가.** L1 경로가 막혀 있음은 코드로 증명했으나(§2-2a), 브라운아웃 히컵·INT WDT·패닉은 실행 시 로그로만 드러난다.
- **32k 크리스털이 실제로 뜨는지 미확인.** 폴백이면 조용히 일어나고 로그도 `esp_log_level_set("*", ESP_LOG_NONE)`(`app_main.c:235`) 이전에 지나간다.
- **PSRAM standby 전류값 미확인.** 16MB 실장은 사용자 확인 사실이나, 미초기화 상태의 실제 소비는 데이터시트조차 확인하지 않았다. 추론(VDD_SPI 상시 급전 + 소프트웨어 제어 불가)까지가 내 근거다.
- **슈퍼바이저 임계·히스테리시스는 도면 벡터 추적 결과**이고 실측된 적이 없다. `E_boot 0.45 J`도 추정치다(같은 문서 §8 미검증 목록).
- **`sdkconfig`의 light sleep 관련 항목이 실제 슬립 전류에 얼마를 기여하는지** 나는 계산만 할 수 있고 측정할 수 없다.

## 5. 이번에 실제로 변경한 코드 — 워치독 해제 진단 스위치

> 원래 지시는 "코드를 수정하지 마라"였으나, 작업 중 사용자가 **"WatchDog 끄는 Mode 하나 만들어줘"** 로 명시적으로 요청하여 추가했다. 진단 목적의 컴파일타임 스위치이며 **기본값 0(비활성)** 이라 현재 빌드 동작은 바뀌지 않는다.

### 변경 파일

| 파일 | 변경 |
|---|---|
| `main/watchdog/wdt_guard.h` | `INGPS_WDT_DISABLED` 스위치 정의(기본 0) + 의미·한계 주석, `#warning` |
| `main/watchdog/wdt_guard.c` | `#if INGPS_WDT_DISABLED` 분기 추가. 공개 API 전부 no-op 화, 모니터 태스크 미생성, `esp_task_wdt_deinit()` 호출. `#else` 아래 기존 구현은 **한 줄도 바꾸지 않음** |
| `main/app_main.c` | 스위치 위치를 가리키는 주석 4줄만 추가(로직 변경 없음) |

### 사용법

`main/watchdog/wdt_guard.h`의 `#define INGPS_WDT_DISABLED  0` → `1` 로 바꾸고 빌드.
(`app_main.c`가 아니라 헤더에 둔 이유: `wdt_guard.c`에서도 보여야 하는데, `app_main.c`에 정의하면 그 번역 단위에만 적용되어 조용히 반쪽만 꺼진다.)

### 꺼지는 것 / 남는 것

| 계층 | INGPS_WDT_DISABLED=1일 때 |
|---|---|
| L1 헬스모니터 태스크 | ❌ **생성 안 함** → **2초 주기 wake 소멸** (이 실험의 핵심 이득) |
| L2 Task WDT | ❌ `esp_task_wdt_deinit()`으로 해제 |
| crash-loop escalation (백오프 딥슬립 / SAFE) | ❌ 비활성 → 재부팅이 나도 딥슬립으로 도망가지 않아 전류 파형에 그대로 보인다 |
| reset reason 로그 | ✅ **유지** (§3-3 판정에 필수) |
| `wdt_guard_reboot()` | ✅ 유지 (워치독이 아니라 명시적 에러 핸들러) |
| L3 Interrupt WDT (300ms) | ⚠ **안 꺼짐** — `sdkconfig:1645` `CONFIG_ESP_INT_WDT` 소관 |
| L5 부트로더 RTC WDT | ⚠ **안 꺼짐** — `CONFIG_BOOTLOADER_WDT_ENABLE` 소관 |

> L2까지 껐는데도 재부팅이 계속되면 원인은 L3/L5 아니면 **브라운아웃/슈퍼바이저**다. reset reason이 갈라준다(§3-3).

### 이 스위치로 무엇을 알 수 있나

`INGPS_BLE_DISABLED=1` + `INGPS_WDT_DISABLED=1` 조합이면 **시스템에 주기적 waker가 하나도 남지 않는다** → light sleep 구간이 사실상 무한 → **센서 상시전류 + 슬립 floor의 순수값**이 측정된다.

| 관측 | 해석 |
|---|---|
| 지속시간이 크게 늘어남 | 워치독 wake 오버헤드가 유의미했다 → §2-2b 확인. 다만 이건 **실험 오염 제거**이지 운영 개선책이 아니다 |
| 거의 그대로 (여전히 mA급) | wake 오버헤드는 무관 → 원인은 **상시전류**(§3순위: PSRAM / 플래시 / ADXL345)나 **클럭 폴백**(§4순위) |
| 여전히 130초, 로그 반복 | 재부팅 루프 확정 → §2-2c(브라운아웃 히컵) |

**⚠ 측정이 끝나면 반드시 0으로 되돌릴 것.** 필드 노드에서 이 빌드는 멈춰도 아무도 살려내지 않는다.

```

```

## 6. 요약 판정

1. **"역전"이 실재한다는 근거가 아직 없다.** #2만 측정 조건(4.61→3.30 V, 210 s)이 기록되어 있고 #1은 없다. 슈퍼캡 에너지는 V²에 비례하므로 V_start 차이 하나로 130 vs 210이 통째로 뒤집힌다. → **1순위는 측정 프로토콜.**
2. **사용자의 워치독 가설은 L1 재부팅 경로에 한해서는 코드상 성립하지 않는다** — `app_main.c:339-340`의 24h 완화가 `:349` arm보다 먼저 실행되고, ACCEL 슬롯은 `last_us=0`이라 검사 자체를 건너뛴다. 다만 **워치독 모니터가 이 빌드의 유일한 waker**라는 점은 사실이고, 그래서 끄고 재는 것이 옳다.
3. **진짜 위험한 갭은 브라운아웃 재부팅 루프가 crash-loop escalation에 안 잡힌다는 것**(`wdt_guard.c:230-233`). 이건 130초를 단독으로 설명할 수 있고, UART 로그 1줄로 즉시 판별된다.
4. **PSRAM 설정 불일치 가설은 기각**(`CONFIG_SPIRAM is not set`, 하위 심볼 부재). 다만 16MB 실장 + 미초기화 = **소프트웨어로 끌 수 없는 상시 standby 전류**라는, 더 나쁜 형태의 문제가 남는다. 양쪽 빌드 공통이라 역전은 설명 못 하지만 mA급 floor의 유력 후보다.

## B. 🔴 최우선 결론 — "두 모드가 ~120초로 수렴했다"는 **아직 성립하지 않는다**

### B-1. #2에 전압 창이 없다. 같은 "120초"가 두 개의 다른 결론을 낸다

#1은 창 전체(4.968→2.343 V)가 있는데 **#2는 시간만 있다.** 부스트(정전력 부하, §2-1순위
근거 C)에서는 시간이 아니라 **에너지**로 비교해야 한다. `E = ½C(V₁²−V₂²) = 0.235(V₁²−V₂²)` J.

#2가 어느 전압까지 갔느냐로 결론이 정반대가 된다:

| 가정 | #2 에너지 | #2 평균전력 | #1을 같은 창으로 환산 | 판정 |
|---|---:|---:|---:|---|
| (i) #2도 **2.343 V**까지 (4.968 시작) | 4.510 J | **37.6 mW** | 37.0 mW | **수렴 실재** → 공통 플로어 문제 |
| (ii) #2는 구 프로토콜대로 **3.30 V**까지 | 3.241 J | **27.0 mW** | 3.30 V 도달까지 **약 88 s** | **역전 지속** (BLE-off가 먼저 죽음) — 수렴 아님 |

(ii)의 88 s는 #1의 에너지 4.510 J 중 3.30 V까지 쓰는 몫이 3.241 J(=72%)라는 계산이다.
즉 **#2가 3.30 V 기준이면 #1은 120초를 못 채우고 88초에 죽은 것**이고, 이건 수렴이 아니라
직전 보고서 §1의 역전이 그대로 남아 있는 것이다.

> **→ #2의 V_start / V_end 없이는 이번 조사의 전제 자체가 확정되지 않는다. §E-1이 최우선.**

### B-2. #1은 슈퍼바이저 컷오프(≈2.52 V) **아래**에서 멈췄다 — 뒤쪽 구간은 부하가 없다

`V_end = 2.343 V`는 TPS3839G25의 `V_off ≈ 2.52 V`보다 낮다(§1-1순위 근거 A).
2.52 V를 지난 순간 EN이 내려가 3.3 V 레일이 죽으므로, **그 아래 구간은 부하가 아니라 누설만
소모한다.** 부하가 실제로 쓴 에너지는:

`0.235 × (4.968² − 2.52²) = 0.235 × 18.331 = 4.308 J`

이 4.308 J를 122 s로 나누면 **35.3 mW** — 그런데 레일은 122초보다 **먼저** 죽었으므로
35.3 mW는 **하한**이다. 실제 부하 전력은 이보다 높다.

### B-3. 그래도 회귀는 실재한다 (에너지로 정규화해도 약 3배)

| 실행 | 부하가 쓴 에너지 | 시간 | 평균전력 | 3.3 V 레일 환산(η=85%) |
|---|---:|---:|---:|---:|
| 구 #2 (08-26, BLE on) | 2.435 J | 210 s | **11.6 mW** | ≈ 2.99 mA |
| 신 #1 (BLE off) | 4.308 J (하한) | 122 s | **≥35.3 mW** | ≥ 9.09 mA |

**약 3.0배 악화** (사용자의 선형 `C·ΔV/t` 비교 10.11/2.93 = 3.45배와도 같은 자릿수).
창이 다르다는 반론은 에너지 정규화로 이미 제거했으므로, **"BLE를 껐는데 예전 BLE-on보다
3배 나쁘다"는 것은 창 차이로 설명되지 않는다.** 공통 항 약 **+6 mA**가 어딘가에서 늘었다.

수렴이 실재한다면(가정 (i)), **부하와 무관한 항이 부하를 압도한다**는 뜻이다. 재부팅 루프는

`4.308 J / 0.45 J ≈ 9.6회` → 122초 동안 약 **12.7초에 한 번** 재부팅이면 관측치가 그대로 나온다.

`main/watchdog/wdt_guard.c:231-233` (현재 워킹트리 기준)
```c
if (s_rtc.magic != WDT_RTC_MAGIC ||
    rr == ESP_RST_POWERON || rr == ESP_RST_BROWNOUT) {
    s_rtc.abnormal_resets = 0;
```
→ 백오프 딥슬립도 SAFE 모드도 영원히 발동하지 않아 루프가 자기제한되지 않는다.

`sdkconfig.defaults`(커밋 `a798cf9`에서 추가된 주석)가 같은 고장 모드를 이미 명문화해 뒀다:

> 슈퍼캡이 마르면 슈퍼바이저가 EN을 내리고, 재축전 후 다시 부팅을 시도하는 **34초 주기 히컵
> 루프**가 된다. 3.3V 레일이 정상적으로 꺼지므로 BOD 로그도 남지 않고, wdt_guard의 crash-loop
> escalation도 POWERON으로 분류되어 작동하지 않는다.

**⚠ 단, 이번 벤치 시험에는 중요한 제약이 있다.** 히컵 루프는 **재충전원이 있어야 지속된다.**
TPS3839G25는 `V_on ≈ 3.07 V > V_off ≈ 2.52 V`(히스테리시스 ≈555 mV)이므로, 배터리/R5가
분리된 순수 캡 방전에서는 2.52 V를 지나면 **다시 켜지지 않는다** → 히컵은 최대 1회다.
반대로 4.968 → 2.52 V 구간에서는 레일이 건강하므로, 이 구간의 재부팅은 브라운아웃이 아니라
**INT_WDT / TASK_WDT / PANIC** 이어야 하고 **셋 다 reset reason 로그를 남긴다.**
→ **배터리 연결 여부(§E-2)가 이 후보의 성립 조건을 가른다.** 판별은 §3-3 그대로.

- 참고: `sdkconfig:2741` `CONFIG_ESP32_RTC_XTAL_BOOTSTRAP_CYCLES=0`(부트스트랩 구동 사이클 없음).
  다만 이 심볼은 **레거시 ESP32용**이라 S3에 적용되는지는 확인하지 못했다 — 단정하지 않는다.

**이건 하드웨어다 — 사용자 지시 5대로 코드로는 확정할 수 없다.** 판별은 §3-4 #1(R5 양단 전압).

### 4순위 — EDLC 전하 재분배 + 정격 근접 충전 (측정 오염)

두 실측 모두 120~210초, 즉 프로젝트 자체 문서가 **"오염 구간"으로 선언한 창** 안에 있다.

`Docs/INGPS_floor전류_측정절차_2026-08-11.md:90`:
> EDLC는 충전 직후 **전하 재분배**를 겪어 단자 전압이 스스로 내려가는데, 이는 **부하 전류와
> 파형상 구분되지 않고** 초기 수 분간은 데이터시트 2 µA보다 훨씬 크게 나타난다.

같은 문서 `:86` "누설은 데이터시트로 빼지 말 것 — **blank run으로 실측한다**", `:98` "blank run이
재분배·누설·온도 영향을 한꺼번에 제거한다". **blank run은 아직 한 번도 수행되지 않았다**(직전
보고서 §1-2: 저장소에 CSV 0건).

그리고 이번엔 조건이 더 나쁘다 — `Docs/INGPS_슈퍼캡_축전시간_분석_2026-08-11.md:40`:
> 슈퍼캡 정격 **5.0 V @65 °C** / 4.2 V @85 °C

**신 #1의 V_start 4.968 V는 정격의 99.4%다** (구 #2는 4.61 V = 92%). EDLC 누설은 정격 근처에서
급격히 초선형으로 증가하고 재분배 droop도 커진다. **부하와 무관한 항이므로 두 모드를 같은
시간으로 수렴시킨다.**

**단 규모는 부족할 수 있다.** +6 mA 전부를 재분배로 돌리려면 캡 쪽에서 ~6 mA 상당이 필요한데,
0.47 F 코인 EDLC의 재분배는 통상 수백 µA~1 mA 상당이다. **기여는 하되 단독 설명은 어렵다**고
본다 — 2·3순위와 합산되는 항으로 취급하는 것이 맞다.

## E. 사용자 확인 요청 (전부 읽기 전용 — 코드 수정 불필요)

### E-1. 🔴 최우선 — #2(BLE 기동, 약 120초) 실행의 **V_start / V_end**

| 항목 | 값 | 비고 |
|---|---|---|
| #2 V_start | ? | #1은 4.968 V |
| #2 V_end (종료 판정 전압) | ? | #1은 2.343 V, 구 #2는 3.30 V |
| #2 배터리 연결 여부 | ? | |

**판정:** #1과 같은 창(4.968→2.343)이면 **수렴 실재** → D-2/3/4로 진행.
구 프로토콜(→3.30 V)이면 **수렴이 아니라 역전 지속** → 이번 조사의 전제가 무너지고 직전
보고서 §1(측정 프로토콜)로 되돌아간다. **이 한 줄이 나머지 전부를 가른다.**

### E-2. 🔴 두 실행 모두 — **배터리/R5가 연결돼 있었는가**

D-2(히컵 루프)의 성립 조건이다. 분리된 순수 캡 방전이면 브라운아웃 히컵은 최대 1회이고,
연결돼 있었다면 R5(100 Ω, 최대 전력 32.4 mW)로 재충전되며 루프가 지속된다.
**참고: 관측된 부하 ≥35.3 mW는 R5가 공급 가능한 32.4 mW를 이미 넘는다** — 배터리가 연결돼
있었다면 정상 동작점이 없고 히컵 루프가 확정적이다.

### E-3. #1(BLE 끔) 실행의 **"122초"를 무엇으로 판정했는가**

BLE-off 빌드는 광고도 없고 I2C 트랜잭션도 없으며 UART도 묵음이다(직전 보고서 §2-2b).
**관측 가능한 출력이 하나도 없다.** 그런데 `V_end = 2.343 V`는 슈퍼바이저 컷오프(2.52 V)보다
낮으므로, 전압 임계로 잡았다면 그 임계가 무엇이었는지 알아야 §B-2의 "레일이 언제 죽었는가"를
확정할 수 있다.

### E-4. 재부팅 여부 — 직전 보고서 §3-3 그대로 (UART 로그의 `WDT_GUARD` 줄 개수)

D-2를 확정/반증하는 유일한 수단이다. `reset reason` 값이 브라운아웃(9)인지 INT_WDT(5)인지
TASK_WDT(6)인지 PANIC(4)인지가 §D-2의 두 갈래를 가른다.
⚠ `consecutive abnormal resets` 숫자는 `wdt_guard.c:231-233` 때문에 신뢰하지 말고 **줄이 몇 번
찍히는지**를 세라.

### E-5. 32 k 크리스털 실동작 — 직전 보고서 §3-4 #1 (R5 양단 DC 전압)

D-3의 유일한 판별법. 457 µA면 46 mV. **같은 보드를 여러 번 전원 재인가하며 반복 측정할 것** —
콜드스타트가 마진 문제라면 **값이 실행마다 튄다**. 그 산포 자체가 D-3의 증거다.

### E-6. blank run (부하 없이 캡만 방전) — D-4 판별

같은 4.968 V까지 충전한 뒤 **ESP 모듈 EN을 강제로 Low**(또는 모듈 미실장)로 두고 동일하게
방전시켜 시간을 잰다. 여기서 나오는 시간이 재분배+누설 단독 기여다.
`Docs/INGPS_floor전류_측정절차_2026-08-11.md`가 **필수**로 규정한 절차인데 아직 미수행이다.

**판정:** blank run이 122초와 비슷하면 → **관측된 것은 부하가 아니라 캡 자체다**(D-4가 1순위로
격상, 펌웨어는 무죄). 훨씬 길면(예: 10분 이상) → 부하가 진짜다(D-2/D-3로 진행).

### E-7. 재측정 시 V_start를 **4.5 V로 낮출 것**

4.968 V는 정격 5.0 V의 99.4%다. 정격 근처의 초선형 누설을 피하고 구 측정(4.61 V)과의 비교
가능성을 확보하려면 두 빌드 모두 **같은, 그리고 더 낮은** 시작 전압을 쓰는 것이 옳다.
종료 판정도 **3.30 V로 통일**해 구 210초 기록과 직접 비교 가능하게 할 것.

  `name`을 읽는다. 코드 기본값은 1000 ms / 3000 ms / +9 dBm이지만 **NVS에 다른 값이 주입돼
  있으면 그것이 이긴다.** NVS는 git 밖이라 08-26과 지금이 같은지 확인할 방법이 없다.
  (`sdkconfig.defaults`가 파티션 테이블을 유지해 erase-flash 없이 올린다고 명시했으므로 **NVS는
  플래시 사이에 보존된다** — 과거에 주입한 knob이 아직 살아 있을 수 있다.) **미확인.**
- **재분배/누설의 실제 크기.** §D-4의 "수백 µA~1 mA"는 EDLC 일반론이고 이 개체의 실측이 아니다.

- **`E_boot ≈ 0.45 J`** 는 직전 보고서에서 넘어온 **추정치**다. §D-2의 "9.6회/12.7초" 산술은 이
  추정치에 전적으로 의존한다.
- **32 k 크리스털이 실제로 뜨는지.** 폴백은 조용히 일어나고, 로그는
  `esp_log_level_set("*", ESP_LOG_NONE)` 이전에 지나간다. **미확인.**
